### 0.4 Weekenders Coffee 精査結果と本案件への適用

2026-10-05に大熊様から提示された `https://www.weekenderscoffee.com/` を、2026-10-06時点の公開サイトで確認した。本項では、**確認できた事実**と、そこからBashiiin! coffeeへ適用する**設計判断**を分ける。

#### A. 参考サイトから確認できた事実

- トップページの主要ナビゲーションは `TOP / NEWS / ABOUT / ONLINE SHOP / ACCESS` と少数に絞られており、名称も短い。
- トップページではNEWSより前に4点の主要画像が配置されている。公開画像は `sl001.jpg`〜`sl004.jpg` で、いずれも700×700pxの正方形画像。
- 4点の内容は、店舗外観・建築/照明のディテール・植物/庭のディテール・焙煎豆で、**同じ被写体を連続させず「場所／質感／自然／コーヒー」を切り替えて見せる**構成になっている。
- トップページの主要情報は、画像の後に `NEWS`、`ONLINE SHOP`、`ACCESS` と続く。情報をカードで大量に囲うより、見出しとリストを中心に整理している。
- `ABOUT` は別ページに分け、コーヒーや空間の思想に関する長い文章はトップページへ詰め込んでいない。トップは入口として簡潔にし、深い説明は別階層へ分ける思想が見られる。
- 参考サイトの公開HTMLから、トップの画像が複数あることは確認できるが、**現在の自動再生の速度・イージング・スライダー実装方式までは、今回取得できた公開情報だけでは断定しない**。

#### B. Bashiiin! coffeeへ採用する設計原則

参考サイトを再現するのではなく、次の原則だけを翻訳して採用する。

1. **写真を第一言語にする**：説明文より先に実店舗・抽出・豆・スイーツ・空間の写真を見せる。
2. **ファーストビューの写真を連続させる**：店舗要望に基づき、複数の許可済み写真を一定速度で横方向へ流す。一般的な「1枚ずつ切り替えるカルーセル」ではなく、写真が連続するギャラリー／フィルムストリップに近い表現を第一候補とする。
3. **文章量を減らす**：トップページで長所を説明しすぎず、1セクション1メッセージを基本とする。
4. **UIを増やしすぎない**：カード、バッジ、影、角丸、装飾ボタンを必要以上に使わず、写真・文字・細い罫線・余白で階層を作る。
5. **写真の被写体を切り替える**：同じコーヒーカップの写真を並べるのではなく、「コーヒー／抽出 → 店内・外観 → 豆・パッケージ → スイーツ → 空間ディテール → カルチャー」のように視点を変える。
6. **白を“背景”として使う**：白地に装飾を足すのではなく、十分な余白そのものをブランドの静けさ・清潔感として使う。
7. **役割をページで分ける**：Bashiiin! coffeeも5ページ構成となったため、TOPには写真と導線、ABOUTには空間・店舗像、COFFEEにはコーヒー／豆、CONTACTにはフォーム、ACCESSには所在地情報を分ける。ただし長文を増やさない。

#### C. 参考サイトから採用しないもの

- Weekenders Coffee固有のページ内容や`NEWS` / `ONLINE SHOP`等の情報配置（**ABOUT / ACCESSの独立ページは店舗の直接指定によって本案件でも採用**する）
- Weekenders Coffee固有のロゴ、書体、コピー、写真、ブランド配色
- 京都らしさを伝えるための和風装飾・町家風意匠の模倣
- ECを前提とした商品一覧・購入導線
- Bashiiin! coffeeの正式要件と競合する固定営業時間やACCESS大セクション

#### D. Bashiiin! coffee側で追加して維持するもの

- 3秒以内に「スペシャルティコーヒーの店」と分かる明示
- `@bashiiin_coffee` で最新営業情報を確認できる導線
- CURRENT BEANSの更新時点・最新性に関する表示
- 3項目の簡易問い合わせフォーム
- 店舗指定の**ACCESS独立ページ**、公開用電話番号は掲載しない
- 営業サンプルから継承するBashiiin! coffeeロゴ、大きな明朝見出し、編集的な英字Eyebrow

## 1. サイトの目的・成功状態

### 1.1 第一目的

**Bashiiin! coffeeがスペシャルティコーヒーを大切にしている店であることを明確に伝え、来店検討につなげる。**

### 1.2 第二目的

Instagramに分散している「営業情報、豆、スイーツ、店内、カルチャー」を**5ページへ目的別に整理**し、TOPから必要な情報へ短い動線で到達できるようにする。TOPを長大な1ページのまま残さず、分離した各ページの役割を明確にする。

### 1.3 第三目的

店舗の個性を、過度な「高級」「隠れ家」「暗いバー」表現に頼らず、**明るさ・清潔感・クラフト感・カルチャー**として表現する。同時に、先方が評価した営業サンプルLPのロゴ、実店舗写真、大きな明朝系見出し、英字Eyebrow、エディトリアルな余白、写真と文字の強いコントラストといったブランドの連続性を維持する。

### 1.4 主要行動

優先順は以下とする。

1. スペシャルティコーヒー・現在の豆・スイーツ等を見る
2. Instagramで最新の営業情報を確認する
3. Instagramで店舗の最新投稿を見る
4. 必要に応じてGoogle Mapsを開く
5. 問い合わせフォームから問い合わせる

Google Mapsへの導線は**ACCESSページ**に整理する。TOPや共通フッターにも必要最小限のリンクを置いてよい。独立ACCESSページは店舗から明示指定されているため必須とする。

## 2. ターゲット・コミュニケーション方針

### 2.1 ターゲット

店舗回答は「特に限定なし」。よって、旧v0.4の「一人客を最優先」といったペルソナ固定は行わない。

想定閲覧者は、Instagram、Google検索、Google Maps、口コミ、知人紹介等をきっかけにBashiiin! coffeeを知り、次の情報を確かめたい人とする。

- どのようなコーヒーを扱っているか
- 現在どのような豆があるか
- スイーツや店内の雰囲気
- 店のカルチャーや活動
- 最新の営業情報
- 問い合わせ方法

### 2.2 伝えたい中心メッセージ

**「スペシャルティコーヒーを中心に、コーヒー・スイーツ・空間・カルチャーを楽しめるBashiiin! coffee。」**

具体的コピーはデザイン・実装段階で整理し、店舗が明示していない製法・評価・人気・客層を事実として追加しない。

### 2.3 写真主体・シンプル表現の原則

2026-10-05の店舗回答を受け、正式版では**説明して売り込むより、実写で魅力を見せる**ことを優先する。

- 長所・強みを長文や大量の箇条書きで説明しない
- 写真、短い見出し、1〜3文程度の短い補助文、余白で理解させる
- ページを増やしたことを長文化の理由にせず、各ページの目的に必要な情報だけを明瞭に見せる
- 「シンプル」は情報を削除しすぎる意味ではなく、来店判断に必要な情報・CTA・アクセシビリティは維持する
- Weekenders Coffeeは写真主体・情報量・トップの写真表現の参考とするが、Bashiiin! coffee固有の要件・ブランドを優先し、構成や表現を複製しない


### 2.4 使用しない方向性

- 「隠れ家的」「隠れ家カフェ」等の表現
- 夜・バーを中心に見せる印象
- 暗さをブランド価値の中心にする表現
- 「一人で過ごす店」と客層を限定する表現
- 根拠のない「人気」「名物」「一番」「最高」等
- 店舗確認のない「自家焙煎」「自家製」「手作り」等



### 2.5 デザイン実装の具体ルール

最新要望とWeekenders Coffeeの精査結果を、実装時に曖昧にしないため次を固定する。

- **ファーストビューは「写真トラック＋固定テキスト領域」**を基本とする。主要コピーやCTA自体を横へ流さない。Mobile幅390pxを優先し、一般的なスマートフォンの縦画面では、スクロール前から写真トラックの一部とスペシャルティコーヒーを示す文言を視認できるレイアウトを第一候補とする。具体的な余白・高さ・配置は初稿で確認する。
- 写真トラックは5〜7枚程度を第一候補とし、最初の1〜2枚には必ずコーヒー／抽出／豆のいずれかを含める。建築・空間写真だけで開始しない。
- 自動横スクロールは「連続移動」を第一候補とし、ドットインジケータ付きの一般的なスライダーUIは原則使用しない。
- 自動で5秒を超えて動き続ける場合は、ユーザーが停止・再開できる手段を用意する。`prefers-reduced-motion: reduce`では自動移動を開始しない。
- HEROの説明は `Eyebrow + H1 + 短い補助文 + 最小限のCTA` に絞り、特徴カードや長い箇条書きを置かない。
- **TOPのCTAは役割を分ける**。スペシャルティコーヒーの詳細へ進む**COFFEE**はサイト内の主要導線、営業日・営業時間の確認先である**Instagram**は最新情報の重要導線とする。どちらを視覚上の最優先リンクとするか・表示順序は**初稿で提案し店舗確認する**。旧1ページLPの「InstagramがPrimary CTA」という分類を、そのまま5ページサイトの全リンク順位に機械的に適用しない。来店前の最新情報への到達性は維持する。
- CTAはアプリ風の大きなボタンを多用せず、HEROではテキストリンクまたは細いアウトラインを第一候補とする。塗りの強いPrimary buttonは問い合わせ送信など明確な最終行動へ優先的に使用する。

### 4.2 画像フォルダ・命名・WebP運用（制作側方針）

画像フォルダ更新時は新しい実ファイルを確認し、サイト内の画像参照と一致させる。ページ／用途を基準に次の整理案を採用する（実際の写真分類を確認して最終調整）。

```text
[本番配信される静的アセット側]
images/
├── shared/        # ロゴ・共通フッター等
├── top/           # 自動横スクロール用の写真
├── about/         # 店内・スイーツ・カルチャー
├── coffee/        # 抽出・豆・パッケージ
└── access/        # 店舗外観・入口等（使用する場合）

[配信対象の外・原則リポジトリ外で別管理]
private-originals/   # 未圧縮原本・撮影元ファイル等（※サイトから配信しない）
```

※ `private-originals/` は**管理場所の概念例**であり、`images/`配下に配置する指示ではない。実際のWorkers Static Assetsの配信ルートが決まったら、原本保管場所と配信対象外であることを設定・デプロイ成果物で検証する。

- 本番配信用の写真は原則`.webp`とする。ロゴ等の透明度・鮮明さ・互換性に合理的な理由がある場合はSVG / PNG等を許容する。
- ファイル名は小文字英数字とハイフンで用途・被写体が分かる命名（例：`coffee-pour-over-01.webp`）。元ファイル名だけに依存しない。
- **原本は上書きせず、原則としてGitHubリポジトリ外かつCloudflare Workers Static Assetsの公開配信対象外に保管する。** `images/originals/`のように公開画像フォルダ内へ原本を置かない。どうしてもリポジトリ内で管理する必要がある場合は、静的アセットの配信ルート外であることを明示し、デプロイ成果物・直接URLで外部アクセス不可を検証してから採用する。
- 複数ページで同じ素材を使う場合は重複ファイルを作らず参照を共用してよい。異なる役割の写真を無意味に繰り返さない。
- ファイル削除・移動・リネーム後は、HTML/CSS/JSのリンク切れと大文字小文字差を必ず確認する。

### 4.3 画像最適化

- 端末サイズに応じリサイズ・圧縮し、必要に応じ`srcset` / `sizes`を使用する。
- 適切なaltを記述。装飾的な画像は意図に応じ空altを使う。
- `width` / `height`または`aspect-ratio`を適切に指定しCLSを抑制する。
- TOPの初期可視範囲でLCPとなる画像のみ優先読み込みし、他の自動スクロール画像は過剰に高優先度へしない。
- below-the-fold画像は原則lazy load。必要以上にJavaScriptで遅延させない。
- 公開不要なEXIF位置情報等を削除し、Web公開前に画質を確認する。

提供JSON-LDに含まれる以下の値は、**提供されたからという理由だけで無検証に公開しない**。

- `alternateName`
- `description` 内の「自家焙煎」「自家製プリンが人気」等
- `priceRange`
- `geo`
- `hasMap`
- `openingHoursSpecification`
- `servesCuisine`
- `acceptsReservations`

特にヒアリングでは営業時間は変動しInstagram等で案内すると確認されているため、**固定の`openingHoursSpecification`は公開前確認なしでは掲載しない。** 正式な曜日・時間を固定できない場合は当該プロパティを削除する。

### 5.3 住所

ヒアリングで確認した住所表記を優先する。

`京都府京都市下京区市之町239-1 やながわビル2F`

郵便番号・表記揺れ・位置情報等は公開前に店舗提供情報と照合する。

## 7. 技術・リポジトリ・公開環境

### 7.1 現行実装

現行リポジトリは静的構成である。

- `index.html`
- `styles.css`
- `script.js`
- `images/`
- GitHub Pages workflow

専用ビルド工程はない。正式版も、要件を満たせる限り**HTML/CSS/JavaScriptの静的構成を継続**する。5つの静的ページを実装し、共通CSS/JavaScriptと共通ヘッダー・フッターの見た目を揃える。不要なフレームワーク移行は行わない。将来のEC化を理由に現時点でReact等へ移行しない。

### 7.1.1 5ページのファイル配置案（制作側提案）

```text
index.html
about/index.html
coffee/index.html
contact/index.html
access/index.html
styles.css
script.js
images/
```

- この配置は推奨パスを満たす一案であり、既存構成・Cloudflare Workers Static Assetsの実際のルーティング設定と整合させる。
- **複数ページのアセット参照パス**：本番サイトをドメイン直下で配信する場合、共通CSS・JavaScript・画像は原則としてルート相対パス（例：`/styles.css`、`/script.js`、`/images/coffee/coffee-beans-01.webp`）で参照する。`/about/`や`/coffee/`等の下層ページでも参照先が変わらないことを確認する。GitHub Pages等のサブディレクトリ配信環境で確認する場合は、その環境のベースパスに合わせて参照先を調整する。本番・確認環境の双方で、CSS・JavaScript・画像の読み込みと404の有無を検証する。
- `POST /api/contact`が静的ページへ誤フォールバックしないようルートとHTTPメソッドを検証する。
- 404、末尾スラッシュ、サイト内リンク、デプロイ時のパスを確認する。
- 複数ページ間でコピー・色・共通ナビに不整合を生じさせない。ビルドツール導入は必要性が認められる場合だけ別途判断する。

### 7.2 リポジトリ／branch運用

- リポジトリ：`misemiru-web/Bashiiin--coffee`
- 現行営業サンプルの基準branch：`main`
- 正式制作は `main` から `formal-production` branchを作成し、**正式制作中は `main` へ直接実装しない**
- `formal-production` 上で**5ページ分のHTML**、共通CSS/JavaScript、画像構成、Workers設定、フォーム、GA4、SEO等を更新する
- 制作中の確認はローカル環境またはCloudflareの確認用Workers環境を使用し、現行GitHub Pagesの営業サンプルを不用意に更新しない
- クライアント最終承認・残金入金・正式公開準備完了後に、営業サンプル保存用のtagまたはbranchを残したうえで正式コードを`main`へ統合する
- 正式公開切替時はGitHub Pagesを停止するか、営業サンプル専用として検索対象外・正式サイトと非競合の状態にする
- READMEは正式公開環境、デプロイ方法、未公開の秘密情報を含めない運用ルールへ更新する
- APIキー、Turnstile secret、認証情報等はGitHubへ保存しない

### 7.3 GitHub Pages

現行GitHub Pagesは営業サンプル／確認用途として扱う。**正式商用サイトの標準公開先にはしない。**

正式公開後は、重複コンテンツを避けるため営業サンプルの公開停止、または検索対象外維持等を実施する。

### 7.4 正式ホスティング・ドメイン

- 独自ドメイン：店舗と相談し決定
- ドメイン・ホスティング：原則店舗名義
- 正式公開の第一候補：**顧客名義 Cloudflare Workers + Static Assets**
- 本案件は問い合わせAPIを同一環境で処理するため、ミセミルWeb事業設計書 v1.5 の「静的LPはCloudflare Pages第一候補」という一般標準に対する**案件固有仕様**としてWorkers + Static Assetsを採用する
- **5ページ分**の静的HTML/CSS/JavaScriptをStatic Assetsとして配信し、問い合わせAPIのみWorkerロジックで処理する
- 静的アセットとWorkerを1つのデプロイ単位として管理する
- 確認環境は顧客名義Cloudflareアカウント上の`*.workers.dev`等を利用可能。正式ドメイン確定前でも確認URLとして使用できる
- DNS、HTTPS、www/apex正規化、canonicalを本番ドメインで確認する
- Cloudflareアカウントは店舗を管理主体とし、ミセミルWebには必要最小限の権限を付与する
- パスワード共有は行わない

### 7.5 問い合わせフォーム・メール送信基盤

- API endpoint：`POST /api/contact`
- 実行基盤：Cloudflare Worker
- bot対策：Cloudflare Turnstile。WorkerからSiteverify APIへ検証し、失敗時は送信しない
- メール通知：Cloudflare Email Service `send_email` bindingを第一候補とする
- 送信先：店舗指定の検証済みメールアドレス。公開前に確定
- 送信元：正式ドメイン確定後、Email Serviceへオンボードしたドメイン上のアドレスを使用
- 保存：DBへ保存しない。個人情報をconsole、GA4、URL、エラーメッセージへ含めない
- 成功条件：Turnstile検証、入力検証、メール送信処理が正常完了した場合のみ成功レスポンスを返す
- GA4 `generate_lead` はフロントエンドが成功レスポンスを受け取った後に1回だけ送信する

### 7.6 Google Analytics 4（GA4）

GA4は**正式導入する**。本番公開前にGA4プロパティ／Webデータストリームを準備し、測定ID（`G-...`）を確定する。

**実装方針**：

- Googleタグを**全5ページの**`<head>`へ適切に設置し、ページ移動後の`page_view`を確認する
- Googleタグは重複設置しない
- 営業サンプル／確認用GitHub Pagesには本番データを混在させない。原則として本番GA4データストリームへの送信対象外とする
- 拡張計測機能を有効化し、**5ページ別の**`page_view`、`scroll`、離脱クリック`click`、CONTACTページでの`form_start`／`form_submit`を計測対象とする
- Instagram、Google Maps等の外部リンクは、拡張計測の離脱クリックを基本に利用し、同一操作を重複計測しない
- 問い合わせフォームが**正常に送信完了した時点**で、GA4推奨イベント`generate_lead`を送信し、キーイベントとして利用する
- `form_submit`はフォーム送信操作の把握、`generate_lead`は実際の送信成功の把握として区別する
- 氏名、メールアドレス、お問い合わせ本文その他の個人情報をGA4のイベント名・イベントパラメータ・URL等へ送信しない
- 現行`script.js`の独自`bashiiin:analytics`／`dataLayer`処理は、本番GA4と重複しないよう整理し、不要なら削除する
- GA4の管理主体は原則として店舗側とし、ミセミルWebには設定・確認に必要な権限を付与する

**公開前確認**：

- Google Tag Assistant等でGoogleタグの設置を確認
- GA4のDebugView／リアルタイムで**5ページの閲覧とページ間遷移**を確認
- Instagram／Google Mapsの離脱クリックを確認
- 問い合わせフォームの`form_start`／`form_submit`を確認
- 正常送信時のみ`generate_lead`が1回記録されることを確認

主な確認指標は、ページ閲覧、スクロール、Instagram／Google Mapsへの遷移、フォーム開始・送信、問い合わせ完了とする。売上・来店数との因果関係はGA4単独では保証・断定しない。

## 8. UI・アクセシビリティ

色・タイポグラフィ・写真主体・余白・共通ナビ・全5ページのビジュアル設計は、**別紙「デザイン定義書 v1.6」（`design-system_v1.6_2026-10-13.md`）を正**とする。旧v1.5は履歴・参考用であり、現行仕様ではない。アクセントカラーを本文・補助ラベル・リンク文字に使用する場合は、デザイン定義書v1.6の文字用濃色トークンを使い、実背景とのコントラストを検証する。

必須基準：

- Mobile First
- 360 / 390 / 430 / 768 / 1024 / 1440pxで破綻しない
- **ページ全体の**意図しない横スクロールなし（TOPの写真トラックは要件として例外）
- 本文16px相当以上を基本
- 主要操作領域44px以上をプロジェクト基準とする
- キーボード操作可能
- 視認できるfocus state
- 色だけで意味を伝えない
- テキストの背景に対するコントラスト4.5:1以上を基本とする
- 非テキストUIのコントラスト3:1以上を基本とする
- `prefers-reduced-motion`対応
- 適切なheading hierarchy / landmark / alt

## 9. モーション

- 基本は控えめなFade / Reveal / Image Reveal程度
- **TOPのHERO画像に、店舗とイメージ一致を確認済みの自動横スクロール写真表現を採用する**
- 自動横スクロールは一定速度で穏やかに動かし、強い加速・急な切替・過剰な視差を使わない
- 重要なコピーやCTA自体を常時移動させない
- ユーザー操作やフォーカスを妨げない。必要に応じ停止・手動操作を用意する
- `prefers-reduced-motion`では自動横スクロールを停止し、静的表示または手動操作へ切り替える
- 常時動く背景や強い3Dは使用しない
- 初回表示時にロゴ演出を入れる場合も短時間・一度のみ

## 10. パフォーマンス

公開後の実ユーザーデータにおける目標：

- LCP 2.5秒以下を目安
- INP 200ms以下を目安
- CLS 0.1以下を目安

これらはCore Web Vitalsの**公開後の実測目標**として扱う。公開前QAではLighthouse / PageSpeed Insights等で重大な性能問題がないことを確認し、INPは実ユーザー操作が必要なためラボ環境ではTBT等も補助指標として確認する。

方針：

- 画像最適化
- HEROで最初に表示される画像のみ優先読み込みし、横スクロール用の全画像を一括で高優先度読み込みしない
- below-the-fold画像のlazy load
- 自動横スクロールは可能な限り軽量に実装し、不要なスライダーライブラリを追加しない
- JS最小化
- 不要な外部ライブラリを増やさない
- Googleタグは公式手順に従い非同期で読み込み、主要表示を不必要にブロックしない
- 外部フォントは必須にしない
